# 建库与资料归属

## 项目范围决定是否入库

项目名称、覆盖模块及排除项记录在根README；用户已有明确定位就沿用，不为固定表单反复追问。多个项目可分别建库，用户明确需要跨项目知识库时按其指定范围组织，不自行扩大到团队全部工作。

| 内容 | 归属判断 |
|---|---|
| 项目业务、状态流转、规则、数据方法、用例、需求及实际问题证据 | 与本项目直接相关才按下表归类，来源和确认状态分别记录 |
| 上下游系统 | 保留本项目所需的调用条件、接口契约、业务采纳和异常预期；详细内部规则引用所属项目，不重复建整套知识 |
| 被测产品接口、架构、源码依据 | 按任务需要保留入口或带版本的必要参考，不复制正在运行的整个工程充当知识库正文 |
| 辅助工具 | 项目内只留必要使用说明与运行入口；脚本、依赖、构建产物和工具开发历史放独立工程或用户指定的库外位置。若工具本身就是被测产品，则按该产品范围判断 |
| 工作管理及通用AI资料 | OKR、绩效/工时、个人计划、跨项目流程制度、Prompt/Skill、AI协作案例和个人项目整理默认不入项目知识库 |
| 知识库自身控制资料 | README、协作规则、来源清单、待确认及简短维护记录按需要保留；不借此引入整套管理统计 |

例如“风控知识库”收策略、分流和结果核查知识；“租赁小程序知识库”收其下单、续租、支付等已纳入范围的链路，相关风控只记录触发及承接契约。示例不是预设全部模块，每位同事以自己的实际范围为准。

## 按检索任务选择结构

用户已确认的精简结构优先，不要求固定五个一级目录。业务规则、测试方法和支撑说明可以合到一个测试指南目录，需求、用例、报告保持清晰入口；图片和必要原件作为附件。下面五类仅为职责映射的示例，不是必须创建的目录。下列业务文档和子目录仅在有资料或任务需要时创建，不预生成空文件和占位用例。

```text
项目测试知识库/
├── README.md
├── 01-项目与业务/
│   ├── 项目概览.md
│   └── 业务规则.md
├── 02-测试指南/
│   ├── 新人上手.md
│   ├── 标准测试流程.md
│   └── 环境与数据准备.md
├── 03-测试用例/
│   ├── README.md
│   ├── 常用回归/
│   ├── 专项回归/
│   └── 需求专项/
├── 04-需求与交付/
│   └── 需求标识或名称/
└── 05-支撑资料/
    ├── 参考资料/
    ├── 工具使用说明.md
    ├── 证据/
    ├── 维护/
    └── 归档/
```

| 位置 | 唯一职责 |
|---|---|
| 根 README | 项目范围及排除项、五类入口、团队约定或等价目录映射；不复制业务规则 |
| 01-项目与业务 | 业务链路、系统边界、术语、角色；已确认规则的条件、状态、结果和依据 |
| 02-测试指南 | 本项目新人路线、测试流程、可重复使用的环境与数据准备方法；跨项目制度放库外，本项目必要约束可简述并引用 |
| 03-测试用例 | 唯一用例正文及定位索引；保持项目主格式和编号，常用回归经过筛选，专项按影响选择，需求专项承载增量 |
| 04-需求与交付 | 按需求关联原始材料、附件、用例及原报告链接；用户以需求池为来源时沿用其实际关联，分析/验收方法归测试指南，不复制平台正文 |
| 05-支撑资料 | 本项目接口、代码入口、架构引用、必要工具使用说明、原始证据、最小维护资料及归档；不收工具程序或通用管理资料，当前业务结论和方法分别回到 01、02 |

待确认事项集中在用户已有主文档的待确认章节或单一清单，其他位置引用；不因模板另建维护目录。证据按需求或任务、环境和执行批次定位。用例索引记录 ID、链接、适用场景和设计成熟状态，不把全部专项作为每轮必测。

受平台约束无法使用标准目录名时，在根 README 保留等价映射，保持职责一致。已有库只在明确要求整理结构时进行迁移，其他任务按映射访问。

## 首次交互顺序

1. 先问：“你希望把知识库建在哪个目录下？请提供目标路径。”如果只提供父目录，再明确项目根目录名和最终路径。已有明确位置不重复询问；位置未明确不自行选址，也不提前扫描资料。
2. 检查目标，在指定位置创建根目录、用户已确认或当前资料确需的目录和导航 README；同名目录和文档检查后复用，不覆盖现有内容或建立重复结构。实际验证目录可用，失败说明原因。
3. 目录建好后再问：“知识库目录已建好。需要整理的资料在哪里？可以提供文件、文件夹路径或在线文档链接。”资料已提供则直接处理，支持分批补充。没有资料说明仅完成目录骨架。
4. 读取指定材料及必要引用，先判断是否属于本库范围，再按正文判定模块、用途和环境/版本。业务归 01，项目测试方法归 02，用例归 03，需求与报告归 04，接口/架构参考、工具使用说明和原始证据归 05。混合材料只提炼与本项目相关部分并保留出处；范围外资料不导入，仅在导入清单注明跳过原因，不默认移动原件。范围不清且影响任务时询问必要定位信息。未读取、无法解析和权限不足分别记录；业务来源不明或冲突进入待确认。
5. 写入前检查已有主题和来源。完全重复引用原件，相关内容合并主文档，不同版本保留关系。一份混合材料原件仅存一处，提炼内容注明出处。库外源文件默认保留，只有用户要求迁移才移走；不擅改原件或覆盖同名不同内容。在线资料优先引用，任务需要时保存带来源与版本的快照。
6. 更新用户已有的来源映射及必要索引；过程记录按用户约定放库外或原有维护位置，记录来源、目标和处理结果，必要时注明未读/冲突原因。平台已有同等清单则直接复用。迁移记录原位置到新位置的映射并修复引用，避免两套正文同时维护。用例保留 ID、主格式及历史执行范围，导入不等于本轮执行通过。不为每批资料生成总结文件。
7. 检查指定资料均有处理结果，包括不属于范围而跳过的材料；已入库内容符合项目定位、归属明确，来源与链接可定位，重复、冲突和缺失如实列出。反馈目录位置、已整理范围和待补材料，不将OKR、通用Prompt或其他项目资料当成本库待补项，不要求一轮补全所有知识，也不补造业务内容。
